# Ceph: A Scalable, High-Performance Distributed File System

## 摘要

我们开发了Ceph，一个具有优秀的性能，可靠性，可扩展性的分布式文件系统。Ceph 通过将分配表替换为一种专为由不可靠对象存储设备（OSD）组成的异构和动态集群而设计的伪随机数据分布函数（CRUSH），最大化地实现了数据与元数据管理的分离。我们通过将数据复制，故障检测和恢复任务分发给运行着专用本地文件系统的 OSD，增加了 OSD 的智能化。一个动态的分布式元数据集群提供了及其有效率的元数据管理，并无缝适应广泛的通用和科学计算文件系统工作负载。性能测量显示在多种工作负载下，ceph有极其优秀的io性能和可扩展的元数据管理，可以支持元数据操作达到 250k/s。

### 1. 介绍

系统设计者一直以来都想提高文件系统的性能，因为它对于整个系统的性能非常关键。特别是科学界和高性能计算社区，推动了分布式存储系统在性能和可扩展性方面的进步，通常能提前几年预示更通用的需求。传统的解决方案，典型如 NFS，提供了一个非常直观的模型，在这个模型中 server 导出一个文件系统层次结构，客户端可以将其映射到本地的命名空间中。尽管应用非常广泛，client/server 模型固有的集中化已被证明是实现可扩展性的重大障碍。

更近期的分布式文件系统架构基于对象存储，原有的机械盘被智能的对象存储设备替代了，OSD 不仅仅是一块盘，它还包括了 CPU，网络和本地缓存包括底层的磁盘或者是RAID。OSD把传统的块层的接口替换成了可以读写更大的变长字节区间也就是对象，把底层块的分配交给了设备自己。client 通常和 metadata server 交互来执行 metadata 操作（open/rename），然后和 OSD 交互来读写，显著的提高了可扩展性。

系统在采取了这种模型后，还继续受到了可扩展性的影响，由于meta data 的分布式的限制。对于传统文件系统的持续依赖，比如分配列表和inode table，以及不愿意将只能下放给 OSD，进一步限制了可扩展性和性能，并增加了可靠性成本。

我们提出了 Ceph，一个分布式文件系统，它提供了卓越的性能和可靠性，同时承诺了无与伦比的可扩展性。我们的架构基于这样一个假设：PB级规模的系统本质上是动态的：大型系统不可避免地是增量构建的，节点故障是常态而非特例，并且工作负载的质量和特征会随着时间的推移而不断发生变化。

Ceph 通过消除文件分配表并将其替换为生成式函数，实现了数据和元数据的解耦。这使得 Ceph 能够利用 OSD 具备的智能特性，将围绕数据访问、更新序列化、数据复制与可靠性、故障检测及数据恢复等方面的复杂性下放到各个节点中。Ceph 采用了一种高度自适应的分布式元数据集群架构，极大地提升了元数据访问的可扩展性，并由此提高了整个系统的可扩展性。我们讨论了驱动我们在架构设计中做出诸多选择的目标与工作负载假设，分析了这些选择对系统可扩展性和性能的影响，并分享了我们在实现功能性系统原型过程中的经验。

### 2 系统概述

Ceph 文件系统有三个主要的组件：

* client，每个实例都提供了一个接近于 posix 的文件系统接口给 host 或者进程
* OSD 集群，存储了所有的数据和元数据
* 元数据集群，管理了文件系统的 namespace ，也协调安全性，一致性和缓存一致性\

我们称 Ceph 的接口是类 posix 语义的，因为我们认为，为了更好地契合应用程序的需求并提升系统性能，适当地扩展接口并有选择放宽一致性语义是合理的。

架构的主要目标是：可扩展性（几百 PB 以上的数据），性能，可靠性。系统的可扩展性是从多个维度进行考量的，不仅包括系统整体的存储容量和吞吐量，还涵盖了针对单个客户端，单个目录或者单个文件的处理性能。我们的目标负载可能包括一些极端的case比如有数十个数百个hosts并发的读取或者写入同一个文件，或者同一个目录里创建文件。这种在运行于超算集群的科学应用中常见的场景，正日益预示着未来通用计算工作负载的发展趋势。更重要的是，我们认识到分布式文件系统的工作负载本质上是动态变化的，随着时间推移，活跃的应用程序和数据集的更迭，系统对数据和元数据的访问模式会出现显著的波动。Ceph 直接解决了可扩展性问题，并同时实现了高性能、高可靠性和高可用性，这主要归功于三个核心设计特性：数据与元数据的解耦、动态的分布式元数据管理，以及可靠性的自治式分布式对象存储。

**数据和元数据的解耦**：Ceph 最大化分离了文件的元数据管理和文件数据存储。元数据操作（open，rename等等）统一的被一个元数据集群管理，而客户端直接和OSD交互进行文件的读写。基于对象的存储长期以来一直期望把底层 block 的分配下放到底层设备来提高系统的可扩展性。然而，现有的基于对象的文件系统通常只是将冗长的，基于每个文件的块列表替换为较短的对象列表，而 Ceph 则彻底消除了分配列表。相反，文件数据被条带化（切分）到命名可预测的对象上，同时，一个名为CRUSH的专用数据分布函数负责将这些对象分配到存储设备上。这使得任何参与方都能通过计算得出构成文件内容的所有对象的名称和位置，从而彻底消除了维护和分发对象列表的必要性，简化了系统设计，并减轻了元数据集群的工作负载。

**动态的分布式元数据管理**：由于文件系统元数据操作在典型文件系统工作负载中占比高达一半，因此高效的元数据管理对系统整体性能至关重要。Ceph 利用了一种基于“动态子树分区”的新颖元数据集群架构，改架构能够自适应且智能地将管理文件系统目录层级的职责，分散到数十个甚至数百个MDS之间。层级式分区保留了每个MDS工作负载的局部性，这不仅促进了高效率的元数据更新，还为激进的预取提供了便利，从而大幅提升了常见工作负载下的系统性能。值得注意的是，元数据服务器之间的工作负载分配完全基于当前的访问模式；这使得Ceph能够在任何类型的工作负载下，有效地利用所有可用的MDS资源，并随着MDS数量的增加实现近乎线性的扩展。

**可靠的自治式分布式对象存储**：由成千上万台设备组成的大型系统本质上是动态的：他们以增量的方式构建，随着新存储设备的部署和旧设备的退役，系统规模会不断地扩张和收缩，设备故障是频繁且在预料之中的；同时，海量的数据在不断地被创建、迁移和删除。所有这些因素都要求数据的分布必须不断演进，以便有效地利用可用资源，并维持预期的数据副本冗余水平。Ceph 将数据迁移、数据复制、故障检测以及故障恢复的责任，全部下放到了实际存储数据的OSD集群；与此同时，在宏观层面上，这些OSD共同为客户端和元数据服务器提供了一个单一的逻辑对象存储池。这种方法使得Ceph能够更有效地利用每个OSD节点上自带的智能（CPU和内存），从而实现具备线性扩展能力的、可靠且高可用的对象存储。

我们将描述Ceph客户端、元数据服务器集群以及分布式对象存储的运行机制，并探讨他们是如何收到我们架构中各项关键特性的影响的。同时，我们也将介绍我们原型系统的当前状态。

### 3 客户端

我们将通过描述 Ceph 客户端的运行机制，来整体介绍 Ceph 各组件的运作方式以及它们与应用程序之间的交互过程。Ceph 客户端运行在执行应用程序代码的每台主机上，并向应用程序暴漏一个文件系统接口。在 Ceph 的原型里，客户端代码完全跑在用户态，可以通过链接它或者挂载一个FUSE文件系统挂载来访问。每个客户端都有自己的文件数据cache，独立于 kernel page或者buffer cache，这使得那些直接链接到该客户端的应用程序能够直接访问这些缓存。

#### 3.1 文件 I/O 和能力

Ceph 文件系统有三个主要的要素：

当进程打开了一个文件，客户端会向 MDS 集群发一个请求。MDS 便利文件系统的层级从文件名字找到 文件 inode，里面有一个独立的 inode number，文件的拥有者，mode，size以及其他的meta。如果文件存在且允许访问，mds 返回 inode number，file size，把文件映射为对象的条带策略等信息。mds 还会告诉 client 一个 capability 字段说明支持哪些操作。capabilities 当前有4个bits，分别控制客户端的读，cache 读，写，buffer 写。未来，capabilities 还会包含 security keys ，clients 通过这些 keys 来向 OSD 证明有读写数据的权限。此后，MDS 对文件 I/O 的参与将仅限于管理能力 capabilities，以维护文件一致性并确保实现正确的文件系统语义。

Ceph 抽象并整合了一系列的条带化策略，将文件数据映射到一系列对象文件中。为了避免文件分配的元数据，对象名字只是把文件 inode 号和 条带号结合了起来。对象的副本通过知名的 CRUSH 算法分配到了特定 OSD 上。例如，一个或多个客户端打开一个文件进行只读访问，MDS 就会授予他们读取并缓存对象内容的权限。一旦掌握了 inode 号，layout 和文件 size，客户端就知道所有的对象文件的名字和他们的存储位置，然后可以直接从 OSD 上读取。任何不存在的对象文件或者字节区间，被定义为文件的洞，一般表现为全零。同样的，如果客户端打开一个文件进行写入，它会被授予带有缓冲机制的写权限；此后它在文件任意 offset 出产生的数据，写入到对应 OSD 上的对象中即可。客户端在关闭文件时交还权限，并向 MDS 提供文件的最新大小，从而重新定义了可能包含文件数据的对象集合。

#### 3.2 客户端同步

POSIX 语义合理地要求：所有的读取操作都必须反映出之前已经写入的数据，并且写入操作必须是原子的（针对同一位置发生重叠的并发写入，其结果必须反映出某种特定的先后发生顺序）。当一个文件被多个客户端同时打开，且存在多个写入者，或者是读取者和写入者混合的情况时，MDS将会撤销之前下发的所有读取缓存和写入缓冲权限，从而强制客户端对该文件 I/O 操作变为同步模式。也就是说，应用程序的每一个读取或者写入操作都将被阻塞，直到收到来自OSD的确认响应，这实际上是将数据更新的串行化和同步的重担，完全交给了存储对应对象的各个OSD 来承担。当写入操作跨越对象边界时，客户端会获取受影响对象上的排他锁，随后立即提交写入操作和解锁操作，以此来实现所需的串行化。类似地，通过获取对象锁并异步刷入数据，对象锁也被用来掩盖大块写入时的延迟。

不足为奇的是，同步 I/O 对于应用程序来说是致命的性能杀手，特别是哪些小块读写的程序。这是因为每次I/O操作都会带来延迟开销--即至少需要与OSD之间进行一次往返。尽管读写共享在通用工作负载中相对少见，但在科学计算应用中却更为常见，而这些应用通常对性能极其敏感。因此，在某些应用程序并不依赖严格一致性的场景下，以牺牲严格的标准合规性为代价来放宽一致性要求，通常是合乎需要的。尽管Ceph 通过一个全局开关支持这种放宽，并且许多其他分布式文件系统对此问题采取了回避策略，但这仍是一种不精确且令人不满的解决方案：要不性能受损，要么在全系统范围内丧失一致性。

正因如此，高性能计算（HPC）社区提出了一系列针对POSIX I/O 接口的高性能计算扩展，Ceph实现了其中的一部分。最值得注意的扩展包括一个用于 open 的 O\_LAZY 标志，它允许应用程序显式地放宽对共享写文件的常规一致性要求。那些注重性能并能自行管理一致性的应用程序（例如，通过写入同一文件不同部分--这是HPC工作负载中的一种常见模式），在原本会被迫执行同步I/O的情况下，现在被允许进行写入缓冲或者读取缓存。如果需要，应用程序可以通过两个额外的调用显式地进行同步：lazyio\_propagate 将指定的字节范围冲刷到对象存储中，而 lazyio\_synchroize 则确保之前所有 propagation 的效果能在随后的读取操作中被反映出来。因此Ceph 的同步模型保持了简洁性：它既通过同步I/O为客户端之间提供正确的读写和共享写语义，又通过扩展应用程序接口，为追求高性能的分布式应用程序提供了放宽一致性的选择。

#### 3.3 Namespace 操作

客户端和文件系统 namespace 的交互是在 mds 集群的管理下的。无论是读取操作还是更新操作，都由 mds 同步执行，以保证串行化，一致性，正确的安全控制以及系统的可靠性。为了简单起见，不会向客户端发放任何元数据锁或租约。特别是对于高性能计算工作负载，callbacks 带来的收益微乎其微，却极有可能付出高昂的复杂性代价。

反而，Ceph 针对最常见的元数据访问场景进行了优化。对每个文件依次执行 readdir 和 stat 是一种极其常见的访问模式，并且在大型目录中是臭名昭著的性能杀手。在 Ceph 中，一次 readdir 操作只需要向 mds 发起单次请求，该请求会获取整个目录的信息，包括其中文件的 inode 内容。默认情况下，如果 readdir 之后紧跟着一个或多个 stat 操作，系统会直接返回刚刚短暂缓存的信息；否则，这些信息将被丢弃。尽管这在某种程度上轻微地放宽了一致性要求，但我们很乐意为了大幅提升性能而作出这种权衡。这种行为被 readdirplus 扩展明确地固化下来，该扩展在返回目录项的同时也返回 lstat 的结果。

Ceph 本可以允许通过更长时间地缓存元数据来进一步放宽一致性要求，就像早期版本的 NFS 通常会缓存 30s 那样。然而，这种做法会破坏一致性，而这种一致性对应用程序来说通常至关重要。例如，那些依赖 stat 操作来判断文件是否被更新的应用程序--它们要么运行出错，要么就只能干等，直到旧的缓存值超时失效。

我们选择在性能受到不利影响的情况下，通过扩展接口来再次提供正确的行为。这种选择在多个客户端同时打开文件进行写入时的 stat 操作中体现得最为明显。为了返回正确的文件大小和时间，mds 会撤销所有写入权限，以暂时停止更新，并从所有写入者那里收集最新的大小和 mtime 值。stat 的回复会返回这些值中的最大值，随后权限被重新下发以允许操作继续进行。虽然停止多个写入者似乎有些极端，但这对于确保正确的串行化是必要的。那些不需要这种连贯行为的应用程序--它们是与自身需求不匹配的 POSIX 接口的受害者--可以使用 statlite 扩展，它通过位掩码指定哪些 inode 字段不需要保持连贯性。

### 4 动态的分布式元数据

元数据操作往往占据了文件系统高达一半的工作负载，并且处于 I/O 的关键路径上，这使得 MDS 集群对整体系统性能起到了决定性的作用。元数据管理也引出了一个重要的分布式文件系统挑战：尽管容量和I/O可以通过增加更多的存储设备来扩展，而元数据操作往往涉及更高程度的相互依赖性，这使得在保障系统高扩展性的前提下，进行复杂的一致性与协同管理变得更加困难。

Ceph文件和目录的元数据非常小，包含文件名和inode。不像传统的文件系统，完全没有文件分配的元数据-对象文件的名字由 inode 号生成，通过 CRUSH 分布到不同的 OSD 上。这简化了元数据的工作负载，允许我们的 MDS 有效的管理非常大的文件集合，而不用考虑到文件的大小。

我们的设计进一步通过采用两层存储策略，尽力将元数据相关的磁盘I/O降至最低；并利用动态子树分区技术，来最大化数据访问的局部性与缓存效率。

#### 4.1 元数据存储

尽管 MDS 集群服务大部分请求是从内存Cache中读取的数据，然而为了安全性，meta 数据的更新必须提交到磁盘里。一组大型、有界且延迟刷新的日志，使得每个元数据服务器（MDS）能够以高效且分布式的形式，快速将其更新后的元数据流式传输到 OSD 集群中。每个 MDS 专属的日志（大小可达数百MB）还能够吸收重复的元数据更新（这在多数工作负载中很常见）。这样一来，当旧的日志条目最终被刷盘到长期存储时，其中许多条目实际上已经失效了。尽管目前的系统原型尚未实现 MDS 的故障恢复功能，但日志架构的设计旨在确保：一旦某个 MDS 发生故障，另一个节点可以快速重新扫描该日志，从而恢复出故障节点内存缓存中的关键数据，并在此过程中重建文件系统的状态。

这种策略实现了两全其美：既能以高效的方式将更新流式写入磁盘，又能大幅降低重复写入的工作量，从而允许长期的磁盘存储布局能够完全针对未来的读取性能进行优化。具体而言，系统将inode 直接嵌入到目录中。这使得 MDS 仅需发起一次 OSD 读取请求，即可预取完整的目录数据，从而充分利用在大多数工作负载中普遍存在的高度目录局部性。每个目录的内容都会被写入到 OSD 集群中，且采用与元数据日志及文件数据完全相同的数据条带化和分布策略。在我们的原型系统中，inode 编号是以区间段的形式分配给各个元数据服务器的，并且被设定为不可变的；不过在未来，可以在文件删除时轻易地讲这些编号回收利用。系统通过一张辅助的锚点表，使得少数具有多个硬链接的inode依然能够通过 inode 编号进行全局寻址--而这一切，都无需引入一张庞大的、稀疏且笨重的全局inode表，从而避免了对占绝对多数的单链接文件造成性能拖累。

#### 4.2 动态子树分区

我们的主副本缓存策略使得针对任何给定的元数据，都由一个具备权威性的单一 MDS 负责管理其缓存一致性，并对更新操作进行序列化。尽管现有的多数分布式文件系统采用某种形式的基于静态子树的分区方式来委派这种权限，但一些近期出现的、处于实验阶段的文件系统则使用了哈希函数来分散目录和文件的元数据，这实际上是以牺牲数据局部性为代价来换取负载均衡。这两种方法都存在严重的局限性：静态子树分区无法应对动态变化的工作负载和数据集；而哈希分布则彻底破坏了元数据的剧不行，从而丧失了进行高效元数据预取和存储优化的关键机会。

Ceph 的 MDS 集群基于一个动态的子树分区策略，该策略如图2所示，能够自适应地将缓存的元数据按层级分布到一组节点上。每个 MDS 使用带有指数时间衰减机制的计数器，来衡量目录层级中元数据的访问热度。任何读写操作都会使受影响的 inode 及其一致向上追溯到根目录的所有祖先节点的计数器递增，从而为每个 MDS 提供一颗能够反映近期负载分布的带权树。系统会定期比较各 MDS 的负载值，并将大小合适的目录子树进行迁移，以保持集群工作负载的均匀分布。共享的长期存储机制与精心设计的命名空间锁相结合，使得这种迁移得以顺利进行：它只需将相应的内存缓存内容直接转移给新的权威节点，而将对缓存一致性锁或客户端全能的影响降到最低。为了安全起见，被导入的元数据会被写入新MDS 的日志中；同时，迁移双方产生的额外日志条目，确保了这种权限转移过程不回收到突发故障的破坏（类似于数据库的两阶段提交）。最终形成的基于子树的分区会保持较粗的力度，以此来最小化路径前缀复制的开销，并保留至关重要的数据局部性。

当元数据被复制到多个 MDS 节点后，inode 的内容分成3个不同一致性语义的组：安全性（owner，mode），文件大小（size，mtime），不可变的（inode 号，ctime，layout）。只读的字段从来不会变，安全和文件锁被独立的状态机管理，每个状态机都有一些状态和迁移的过程以减少锁的竞争。比如，在路径遍历时需要检查 owner 和 mode ，但它们几乎不会变，需要的状态很少，而文件锁对应的client 的接入状态会非常多，因为它控制着 MDS 颁发客户端能力的权限。

#### 4.3 流量控制

按照目录按照层级拆分到多个节点上，可以均衡大部分的工作负载，但无法总是应对‘热点’或者流量突刺问题--也是大量客户端同时访问同一个目录或文件的情况。Ceph 会利用它对元数据‘热度’的了解，仅在必要时，才将热点数据进行大范围的分布；这样在常规情况下，就不会产生相关的性能开销，也不会破坏目录的局部性。对于那些被高频读取的目录内容，Ceph 会选择性地将他们复制到多个节点上，以此来分担负载。对于那些极其庞大，或者正承受极高并发写负载的目录，系统会根据文件名进行哈希，将其内容分散到整个集群中。这种做法以牺牲目录的局部性为代价，换取了负载的均衡分布。这种自适应的方法使得 Ceph 能够涵盖范围极其广泛的分区粒度。在文件系统特定的场景和特定的区域中，它能够精准应用最有效的策略，从而兼获粗粒度分区和细粒度分区带来的优势。

每一个MDS的响应，都会向客户端提供关于相关 inode 及其祖先目录的‘权威节点’和任何‘副本’的最新信息，从而让客户端能够学习到它们所交互的那部分文件系统的元数据分区情况。未来的元数据操作，将根据给定路径已知最深的前缀，被直接路由到权威节点或随机的副本节点。通常情况下，客户端会获知冷门元数据的位置，并能直接联系到对应的 MDS。然而，对于访问热门元数据的客户端，它们会被告知这些元数据存在于不同的或多个MDS节点上。这有效地限制了‘认定某块特定元数据只存在于某一个特定MDS上’的客户端数量，从而在潜在的热点和流量突刺发生之前，就将它们驱散了’。

### 5 分布式对象存储

从宏观层面来看，Ceph 客户端和元数据服务器将对象存储集群（可能包含数万至数十万个OSD）视为一个统一的逻辑对象存储和命名空间。Ceph 的可靠自主分布式对象存储（RADOS）通过将对象复制、集群扩容、故障检测与恢复等管理任务以分布式方式交由OSD负责，实现了存储容量和整体性能的线性扩展。

#### 5.1 CRUSH 数据分布

Ceph 必须在一个由数千个存储设备组成、不断演变的集群中分布PB级数据，从而有效利用各设备的存储空间和带宽资源。为避免资源失衡（例如，新部署的设备大多处于空闲或为存储数据的状态）或负载不对称（例如，新增的热点数据仅集中在新设备上），我们采用以下策略：随机分布新数据，将现有数据的随机子集迁移至新设备，并均匀地重新分布被移除设备上的数据。这种随机化方法具有很强的鲁棒性，能够在各种潜在工作负载下取得同样良好的效果。

Ceph 首先使用一个简单的哈希函数将对象映射到归置组（Placement Group PG），并通过可调节的位掩码控制PG的数量。我们选择的配置会使每个OSD大约对应100个PG，从而在OSD利用率的波动与每个OSD需要维护的复制相关元数据量之间取得平衡。

随后，系统使用CRUSH（Controlled Replication Under Scalable Hashing，可扩展哈希下的受控复制）将PG分配给OSD。CRUSH 是一种伪随机数据分布函数，能够高效地将每个PG映射到一个有序的OSD列表，用于存储对象的各个副本。

这种方法与传统方法（包括其他给予对象的文件系统）不同，因为其数据放置不依赖任何数据块列表或对象列表元数据。为了定位任意对象，CRUSH 只需要该对象所属的PG和一份OSD集群映射图。后者是对构成存储集群的设备所作的紧凑、分层描述。

这种方法有两个主要优点：第一，它是完全分布式的，任何参与方--客户端、OSD、MDS--都可以独立计算出任意对象的位置；第二，集群映射图很少更新，因而几乎不需要交换与数据分布式有关的元数据。通过这种方式，CRUSH 同时解决了数据分布问题（“数据应该存储在哪里”）和数据定位问题（“数据存储在了哪里”）。设计上，存储集群的微小变动几乎不影响PG映射，从而最大程度的减少了由设备故障或集群扩展引起的数据迁移。

集群映射图的层次结构会与集群的物理或逻辑组成以及潜在故障源相对应。例如，对于一个由 OSD 装满托盘、托盘装满机柜、机柜排列成行的部署环境，可以构建一个四级层次结构。每个OSD还具有一个权重值，用于控制分配给他的相对数据量。CRUSH 根据放置规则将 PG 映射到 OSD；这些规则定义了副本数量以及数据放置需要满足的各种约束。例如，可以将每个PG复制到三个OSD上：这些OSD全部位于同一排机柜中，以减少跨排复制流量；但分别位于不同的机柜中，以降低电源电路或接入交换机故障造成的影响。集群映射图还包含已宕机或非活动设备的列表，以及一个纪元编号。每当映射图发生变化时，纪元编号都会递增。所有发送给OSD的请求都会携带客户端所使用的映射图纪元，从而使各参与方能够就当前的数据分布达成一致。相互协作的OSD会共享集群映射图的增量更新；如果客户端使用的映射图已经过期，OSD还会将这些更新附带在响应中返回给客户端。

#### 5.2 数据复制

与 Lustre 等系统不同--这类系统假设可以借助 RAID 或 SAN 上的故障切换等机制构建足够可靠的 OSD--我们认为，在PB或EB级系统中，故障将是常态而非例外，并且在任何时刻都很可能有多个OSD无法工作。为了以可扩展的方式维持系统可用性并保障数据安全，RADOS 采用一种主副本复制的变体来自行管理数据复制，同时尽量降低复制对性能的影响。数据以归置组为单位进行复制，每个 PG 都会被映射到一个由n个OSD组成的有序列表，以实现n副本的复制。

客户端将所有写请求发送给对象所属PG 中第一个未发生故障的OSD，即主 OSD。主OSD为该对象和PG分配新的版本号，并将写请求转发给其他副本OSD。每个副本应用更新并向主OSD响应后，主OSD才在本地应用该更新，并向客户端确认写入完成。读请求则发送给主 OSD。

这种方法使客户端不必处理副本之间的同步或串行化等复杂问题；当存在其他写入者或正在进行故障恢复时，这些问题尤其棘手。它还将数据复制所消耗的带宽从客户端转移到OSD集群内部网络中，因为我们预计后者拥有更充足的网络资源。

复制过程中发生的副本OSD故障可以暂时忽略，因为后续的恢复过程能够可靠地恢复各副本之间的一致性。

#### 5.3 数据安全

在分布式存储系统中，将数据写入共享存储主要有两个目的。

第一，客户端希望自己的更新能够被其他客户端看到。这一过程应该尽可能迅速：写入应当尽快变得可见，尤其是在存在多个写入者，或者读写操作混合进行、迫使客户端以同步方式运行时。

第二，客户端希望明确获知，其写入的数据已经安全地复制并持久化到磁盘，即使发生断电或其他故障也不会丢失。

RADOS 在确认更新时，将“同步可见性”与“数据安全性”区分开来，使Ceph既能提供低延迟的更新以支持高校的应用程序同步，又能提供定义明确的数据安全语义。图4 展示了对象写入过程中发送的消息。

主 OSD 将更新转发给各副本，当更新已经应用到所有 OSD 的内存缓冲区缓存后，主 OSD 向客户端返回确认，使客户端上的同步 POSIX 调用得以返回。当数据安全地持久化到磁盘后--这可能发生在数秒之后--系统再向客户端发送最终的提交确认。尽管这会增加客户端延迟，但系统只有在更新被完整复制后才向客户端发送ack，从而能够在任意一个 OSD 发生故障时无缝容错。默认情况下，客户端还会继续缓存这些写入，直至收到 commit，以避免同一归置组中的所有 OSD 同时断电时发生数据丢失。

在此类故障后的恢复过程中，RADOS 会在开始接受新更新之前，允许在一个固定的时间窗口内重放此前已经确认、因而顺序也已经确定的更新。

#### 5.4 故障探测

及时故障检测对于保障数据安全至关重要，但当集群扩展到数千台设备时，故障检测会变得十分困难。对于某些故障，例如磁盘错误或数据损坏，OSD 可以主动上报。然而，如果某类故障导致OSD在网络上不可达，就必须进行主动监测，RADOS 采用分布式监测机制：每个OSD负责监测与其共享同一PG的其他OSD。在大多数情况下，已有的副本复制流量可以被动证明对端仍然存活，因此不需要产生额外的通信开销。如果某个OSD最近一直没有收到某个对等OSD的消息，便会向其发送显示的ping请求。

RADOS 从两个维度判断 OSD 的存活状态：一是该 OSD 是否可达，而是 CRUSH 是否仍会向其分配数据。一个无响应的 OSD 最初会被标记为 down。此时，他在各个归置组中承担的主 OSD 职责--例如更新的串行化和数据复制--会暂时转移给相应 PG 有序 OSD 列表中的下一个OSD。

如果该 OSD 未能迅速恢复，它就会被标记为 out，从而推出数据分布。随后，每个受影响的PG 都会加入另一个OSD，并将其内容重新复制到该OSD上，以恢复规定的副本数量。

如果客户端仍有提交给故障OSD的未完成操作，只需将这些操作重新提交给新的主 OSD。

由于各种网络异常都可能导致 OSD 连接间歇性中断，因此系统由一个小型 monitor 集群集中收集故障报告，并过滤暂时性或系统性问题，例如网络分区。

monitor 通过选举，主动监测对等节点、短期租约和两阶段提交，共同提供对集群映射图的一致切可用的访问。当集群映射图因故障或恢复而更新后，受影响的OSD会收到增量更新；随后，这些更新会附带在现有的OSD间通信中，逐步传播到整个集群。

分布式监测机制可以迅速发现故障，又不会给monitor带来过重负担；当不同节点对故障状态产生不一致判断时，则通过集中仲裁加以解决。

最重要的是，遇到系统性问题时，RADOS 只会将 OSD 标记为down，而不会将其标记为 out，从而避免触发大规模的数据重新复制，例如，当半数 OSD 因断电而失效时，如果立即将他们全部标记为 out，系统就可能尝试重建这些 OSD 上的所有副本，不仅产生巨大的恢复流量，还可能造成严重的容量压力。

#### 5.5 恢复和集群更新

OSD 集群映射表会因 OSD 故障、OSD 恢复以及部署新的存储设备等显示的集群变更而发生变化。Ceph 以统一的方式处理所有这类变化。

为了加快恢复过程，OSD 会为每个对象维护一个版本号，并为每个归置组保存一份近期变更日志，其中记录被更新或删除对象的名称及版本。这种机制类似于Harp 中的复制日志。

当一个处于活动状态的 OSD 收到更新后的集群映射表时，他会遍历本地存储的所有归置组，并计算相应的CRUSH 映射，以确定自己负责哪些 PG，以及在其中充当主 OSD 还是副本 OSD。

如果某个 PG 的成员发生了变化，或者该 OSD 刚刚启动，那么它必须与该PG中的其他 OSD 进行对等协商。对于采用副本机制的PG，OSD 会将自己当前的PG版本号提供给主 OSD。

如果该 OSD 是这个PG的主OSD，它就会收集当前副本和原有副本的PG版本号。如果主OSD没有最新的PG状态，它会从该PG当前或先前的OSD中获取近期的PG变更日志；必要时，也可以获取完整的内容摘要，从而确定该 PG 正确且最新的内容。

随后，主 OSD 会向每个副本发送增量日志更新；必要时则发送完整的内容摘要，从而使所有参与方都清楚该PG中应当包含哪些内容，即使各 OSD 本地存储的对象集合可能与之不一致。只有在主OSD确定了PG的正确状态，并将其告知所有副本之后，才允许对该PG中的对象执行 I/O 操作。

随后，各 OSD 分别负责从其对等OSD获取本地缺失或已经过期的对象。如果某个OSD收到针对过期或缺失对象的请求，它会暂缓处理该请求，并将相应对象移至恢复队列的最前端，优先进行恢复。

例如，假设osd1发生故障并被标记为down，随后osd2接替他成为pgA 的主 osd。如果 osd1 恢复，它会在启动时请求最新的集群映射图，monitor 则会将它标记为 up。当osd2收到由此产生的映射表更新时，它会发现自己不再是 pgA 的主OSD，于是将 pgA 的版本号发送给 osd1。osd1 随后从 osd2 获取 pgA 近期的日志条目，并告知 osd2，双方现在已经掌握移植的最新 pg 内容信息，之后，osd1 便开始处理请求，同时在后台恢复发生过更新的对象。

由于故障恢复完全由各个 osd 自主驱动，受故障OSD影响的各个pg可以并行恢复，而且很可能分别恢复到不同的替代OSD 上。这种方法基于快速恢复机制，能够缩短恢复时间，并提高整体数据安全性。

#### 5.6 对象存储和 EBOFS

尽管许多分布式文件系统使用 ext3 等本地文件系统来管理底层存储，但我们发现，这些文件系统的接口和性能并不适合对象存储工作负载。现有的内核接口使我们难以准确判断对象更新何时已经安全地持久化到磁盘。同步写入或日志机制虽然能够提供所需的安全性，却会带来高昂的延迟和性能开销。更重要的是，POSIX 接口不支持将数据与元数据作为一个原子事务进行更新，而这种能力对于维持RADOS的一致性十分重要。

Ceph 的每个OSD改用 EBOFS 来管理本地对象存储。EBOFS是一种基于区段和B树的对象文件系统。EBOFS完全在用户空间中实现，并直接访问裸块设备。这使我们能够自行定义对象存储接口和更新语义，将用于同步的“更新串行化”与用户保障安全的“磁盘持久化”分离开来。

EBOFS支持原子事务，例如在一个事务中写入多个队形并更新其属性。当内存缓存完成更新后，更新函数即可返回；而当更新真正持久化到磁盘时，系统则通过异步方式发出提交完成通知。

除了能够提供更大的灵活性并降低实现难度之外，用户态的方案还避免了与linux vfs 和页缓存进行繁琐的交互；这两者原本是针对不同的接口和工作负载而设计的。

大多数内核文件系统会延迟一段时间后才将更新刷写到磁盘，而 EBOFS 则会积极地调度磁盘写入；如果后续更新使某些尚未执行的I/O操作变得多余，EBOFS 就会取消这些操作。

这种方式能够为底层磁盘调度器提供更长的I/O请求队列，从而提高调度效率。采用用户空间调度器，也使系统更容易进一步为不同工作负载设置优先级，或者提供服务质量（QoS）保证。

EBOFS 设计的核心是一套健壮、灵活且完全集成的B树服务，用于定位磁盘上的对象、管理块分配，以及为对象集合（归置组）建立索引。

块分配以区段为单位，即使用“起始位置与长度”二元组，而不是块列表，从而保持元数据的紧凑型。磁盘上的空闲块区段会按照大小分组，并按照物理位置排序。借助这种组织方式，EBOFS 可以迅速找到靠近当前写入位置或磁盘上相关数据的空闲空间，同时抑制长期碎片化。

除每个对象的块分配信息外，其他所有元数据都会保存在内存中，以提升性能并简化实现；即使对于大容量存储卷，这些元数据的体积也相当小。

最后，EBOFS 会广泛采用写时复制机制；出了更新超级块之外，数据始终被写入磁盘上尚未分配的区域。

### 6 性能和可扩展性的评估

我们通过一系列微基准测试对原型系统进行评估，以展示其性能、可靠性和可扩展性。在所有测试中，客户端、OSD和MDS均以用户态进程的形式运行在一个配备SCSI磁盘的双处理器Linux集群上，并通过TCP进行通信。通常，每个OSD或MDS独占一台主机运行；而在生成测试负载时，数十乃至数百个客户端实例可能会共享一台主机。

#### 6.1 数据性能

EBOFS 提供了更优异的性能和更明确的数据安全语义；与此同时，CRUSH实现的数据均衡分布，以及将数据复制与故障恢复任务下放给OSD的设计，使系统的总体I/O 性能能够随着OSD集群规模的扩大而扩展。

#### 6.1.1 OSD 吞吐

我们首先测量一个由14个 OSD 节点组成的集群I/O性能。图5展示了在不同写入大小和不同副本数量下，每个OSD的吞吐量。测试负载由另外20个节点上的400个客户端产生。

系统性能受限于裸磁盘带宽（约58MB/s），图中以水平线表示。当OSD数量固定时，数据复制会使磁盘I/O量增加到原来的两倍或3倍，因此客户端能够获得的数据吞吐率也会相应降低。

<figure><img src="../.gitbook/assets/image (49).png" alt="" width="375"><figcaption></figcaption></figure>

图6对比了EBOFS和一些通用文件系统（ext3，ReiserFS，XFS）在Ceph工作负载上的性能。客户端同步的写大文件，16MB的条带，然后把他们在读回来。虽然 EBOFS 的粗粒度线程与锁机制会影响小块读写性能，但当写入大小超过32KB时，它几乎能够跑满可用的磁盘带宽。

在读取负载下，EBOFS的性能明显优于其他文件系统，因为数据在磁盘上以区段形式布局，并且区段大小与写入大小相匹配，即使写入块非常大也是如此。

上述性能是在一个全新的文件系统上测得的。早起EBOFS设计的实践经验表明，它产生的碎片可能显著少于ext3；不过，我们尚未在经过长期使用的文件系统上评估当前实现。无论如何，我们预计 EBOFS 老化后的性能不会逊于其他文件系统。

#### 6.1.2 写延时

<figure><img src="../.gitbook/assets/image (51).png" alt="" width="375"><figcaption></figcaption></figure>

图7 展示了在不同写入大小和副本数量下，单个写入客户端的同步写入延迟。由于主OSD会同时将更新转发给所有副本，因此，对于小块写入，即使副本数量超过两个，延迟也只会略有增加。

对于较大的写入，数据重传的开销会成为主要因素。例如，1MB写入在单副本情况下耗时13ms，而在三副本情况下耗时增加到2.5倍，即33ms。

对于超过128KB的同步写入，Ceph客户端会通过获取排它锁，然后异步地将数据刷写到磁盘，从而在一定程度上掩盖这种延迟。

另一种选择是，允许共享写入的应用程序使用O\_LAZY。在放宽一致性要求后，客户端可以缓存小块写入，只向OSD提交大块的异步写入。此时，应用程序能够感受到的延迟，主要发生在客户端缓存被写满、必须等待数据刷写到磁盘的情况下。

#### 6.1.3 数据分布和可扩展性

Ceph的数据性能可以根据OSD的数量线形扩展。CRUSH以伪随机方式分布数据，因此OSD的空间利用率可以用二项分布或正态分布准确建模--这正是理想随机过程所呈现的结果。随着PG数量增加，各 OSD 利用率的差异会逐渐减小：当每个 OSD 对应100个PG时，利用率的标准差为10%；当每个OSD对应1000个PG时，标准差则降至3%。

<figure><img src="../.gitbook/assets/image (52).png" alt="" width="375"><figcaption></figcaption></figure>

图8展示了集群扩展过程中每个OSD的写入吞吐量。测试分别采用CRUSH、简单哈希函数和线性条带化策略，将4096个或32768个PG分布到可用的OSD上。

线形条带话能够实现完全均衡的负载和最大的吞吐量，因此可作为对比基准。但是，它与简单哈希函数一样，无法妥善应对设备故障或 OSD 集群的其他变化。

由于CRUSH和哈希函数的数据放置具有随机性，当PG数量较少时，系统吞吐量也较低：OSD利用率的差异较大，导致各 OSD 的请求队列长度在相互关联的客户端负载下逐渐分化。设备有较小概率出现空间占用过高或负载过重的情况，进而拖累整体性能。对于这种情况，可以在集群映射表中对相关OSD进行特殊标记，使CRUSH将其任意比例的数据分配转移到其他OSD上。

与哈希和线形条带化策略不同，CRUSH不仅能够维持均衡的数据分布，还能在集群扩容时尽量减少数据迁移。对于包含n个OSD的集群，CRUSH的计算复杂度为O（logn），单次计算仅需几十微秒，因此可以支持扩展到数十万个OSD的集群。

#### 6.2 元数据性能

Ceph 的 MDS 集群提供了增强的 POSIX 语义和优秀的扩展性。我们用一种不包含任何数据 I/O 的部分工作负载来衡量性能；在这些实验中，OSD 仅用于存储元数据。

#### 6.2.1 元数据更新延迟

我们首先考察元数据更新产生的延迟。单个客户端连续创建一系列文件和目录；为了保障数据安全，MDS 必须将这些操作同步写入由多个OSD构成的集群日志。

我们考虑两种 MDS 配置：一种是无本地磁盘的MDS，其全部元数据都存储在共享 OSD 集群中；另一种则配有本地磁盘，并将该磁盘作为其日志的主 OSD。

图 9.a 展示了两种配置在不同元数据副本数量下的元数据更新延迟，其中副本数量为零表示完全不记录日志。日志条目首先写入主 OSD，然后复制到其他副本OSD。

使用本地磁盘时，从MDS到写本地主 OSD 的第一次传输几乎不产生延迟。因此，这种配置采用两副本复制时的更新延迟，与无本地磁盘配置采用单副本时的延迟相近。

在这两种配置汇总，副本数量超过两个后，增加副本所产生的额外延迟都很小，因为各副本会并行执行更新。

#### 6.2.2 元数据读延迟

元数据读取操作的行为更加复杂。图 9b 展示了客户端遍历 10000 个嵌套目录时所消耗的累计时间；遍历过程中，客户端会对每个目录执行一次readdir，并对每个文件执行一次 stat。预热后的 MDS 缓存可以缩短 readdir 的执行时间。随后执行的 stat 操作不受影响，因为 inode 的内容嵌入在目录中，只需访问一次 OSD，就能将完整的目录内容载入MDS 缓存。

通常，对于较大的目录，stat 操作的累计耗时会占据主要部分。使用 readdirplus 可以避免后续与 MDS 的交互，因为该操作会显式地将 stat 和 readdir 的结果合并在一次请求中返回。

另一种方法是放宽 POSIX 语义，允许紧随 readdir 之后的 stat 请求直接由客户端缓存提供结果；这是 Ceph 的默认行为。

#### 6.2.3 元数据扩展性

我们使用 LLNL 的alc linux 集群中一个包含430个节点的分区，评估元数据服务的可扩展性。

<figure><img src="../.gitbook/assets/image (53).png" alt="" width="355"><figcaption></figcaption></figure>

图 10 展示了每个 MDS 的吞吐量随 MDS 集群规模的变化情况。因此，如果曲线保持为一条水平线，就表示系统实现了理想的线性扩展。该工作负载由深度为4层的嵌套目录构成，每个目录中包含10个文件和10个子目录。随着集群规模扩大，每个 MDS 的平均吞吐量从小型集群中的每秒 2000 次操作，下降到使用 128 个MDS 时的每秒约1000次操作，即扩展效率约为50%，但总吞吐量仍超过每秒10万次操作。

在 makefiles 工作负载中，每个客户端都会在同一个目录内创建数千个文件。当检测到较高的写入负载时，Ceph 会对该共享目录进行哈希分区，并放宽其 mtime 的一致性要求，从而将工作负载分散到所有 MDS 节点上。openshared 工作负载通过让每个客户端反复打开和关闭10个共享文件来测试读共享。在openssh 工作负载中，每个客户端都会在自己的私有目录中，重放一段预先采集的文件系统编译访问轨迹。其中一个变体共享 /lib，产生中等程度的共享；另一个变体则共享 /usr/include，该目录会被机器频繁地读取。

openshared 和 openssh + include 的读共享程度最高，表现出的扩展性也最差。我们认为，这是由于客户端未能合理地选择副本。openssh + lib 的扩展性甚至优于易于直接拆分的 makedirs 工作负载，因为它包含的元数据修改相对较少，共享程度也较低。

我们还认为，在较大的 MDS 集群中，网络争用或消息传递层的线程机制进一步降低了性能。不过，由于我们能够独占使用该大型集群的时间有限，因此无法对此进行更深入的调查。

<figure><img src="../.gitbook/assets/image (54).png" alt="" width="375"><figcaption></figcaption></figure>

图 11 展示了在makedirs 工作负载下，由 4个、16个、64个基点组成的 MDS 集群中，操作延迟与每个MDS吞吐量之间的关系。规模较大的集群存在负载不够均衡的问题，因而每个MDS 的平均吞吐量较低，但集群的总吞吐量显然要高得多；如此同时，操作延迟也会略有增加。

尽管没有实现完全理想的线性扩展，我们的原型系统使用 128 个MDS节点时，每秒仍可处理超过 25万次元数据操作（128个节点，每个节点约2000次/秒）。

由于元数据事务与数据I/O相互独立，而且元数据大小不随文件大小变化，因此，根据平均文件大小的不同，这种处理能力足以支持数百PB乃至更大规模的存储系统。

例如，在LLNL的BlueGene/L上，科学计算应用创建检查点时，可能涉及6.4万个计算节点，每个节点配备两个处理器，并分别向同一目录下的不同文件写入数据，这与 makefiles 工作负载类似。现有存储系统的元数据处理能力峰值仅为每秒 6000 次操作，完成一次检查点可能需要数分钟；而一个由 128个节点组成的Ceph MDS 集群可以在两秒内完成。

假设每个文件只有10MB--按照高性能计算的标准，这一文件规模相当小--并且每个OSD能够维持50MB/s的吞吐量，那么这样的集群可以达到 1.25 TB/s的写入速度，足以跑满 25000 个OSD；如果考虑数据复制，则可跑满50000个OSD。若每个 OSD 的容量为 250GB，那么整个系统的容量将超过 6PB。

更重要的是，Ceph 的动态元数据分布机制使任意规模的 MDS 集群都能够根据当前工作负载重新分配资源。即使所有客户端访问的元数据最初都归属于同一个 MDS，系统仍可动态地将负载扩散到其他MDS。因此，与任何静态分区策略相比，Ceph都具有明显更强的通用性和适应能力。

### 7 经验

令我们颇感惊喜的是，以数据分布函数取代文件分配元数据，竟在如此大的程度上简化了整个系统设计。尽管这对分布函数本身提出了更高的要求，但当我们明确这些具体要求后，CRUSH 成功提供了所需的可扩展性、灵活性和可靠性。

这种设计及大地减轻了元数据管理负担，同时使客户端和OSD都能够完整、独立地掌握数据分布情况。后者使我们可以将数据复制、迁移、故障检测和恢复等职责交由OSD承担，以分布式方式实现这些机制，从而有效利用各 OSD所配备的CPU 和内存资源。

RADOS 还为一系列能够自然融入 OSD 模型的未来增强功能提供了基础，例如类似google 文件系统的位错误监测，以及类似AutoRAID的、根据工作负载动态调整数据副本数量的机制。

尽管使用现有的内核文件系统来实现本地对象存储颇具吸引力--许多其他系统也采用了这种做法--但我们很早就意识到，专门针对对象工作负载设计的文件系统能够提供更好的性能。

我们没有预料的是，现有文件系统接口与我们的需求之间竟存在如此大的差距；这一点在开发RADOS的数据复制和可靠性机制时变得尤为明显。

出乎意料的是，EBOFS 在用户空间中的开发十分迅速，不仅提供了令人满意的性能，还暴露了一套与我们的需求高度契合的接口。

Ceph 项目带给我们的一个重要经验是：MDS 负载均衡器对于系统的整体可扩展性至关重要，而决定在何时将哪些元数据迁移到何处，则是一个非常复杂的问题。

尽管从原理上看，我们的设计和目标似乎相当简单，但在实践中，要将不断变化的工作负载分布到上百个 MDS 上，仍会遇到许多微妙而复杂的问题。尤其值得注意的是，MDS的性能收到多种因素的制约，包括 CPU、内存、网络和I/O；在任何时刻，其中任意一项都可能成为性能瓶颈。

此外，总吞吐量与公平性之间的平衡也很难进行量化。在某些情况下，不均衡的元数据分布反而能够提高系统的整体吞吐量。

客户端接口的实现比预期更具挑战性。尽管使用fuse避开了内核开发，极大地简化了实现，但它也带来了一系列自身特有的问题。DIRECT\_IO可以绕过内核页缓存，却不支持mmap，因此我们不得不修改fuse，通过使未被修改的缓存页失效来规避这一问题。fuse坚持自行执行安全检查，导致即使是简单的应用程序调用，也会产生大量 getattr 操作。此外，内核空间与用户空间之间以页为单位进行I/O，也限制了系统的整体I/O速率。

虽然直接链接Ceph 客户端库可以避开fuse的这些问题，但在用户空间中重载系统调用又会引入一系列新的问题，其中大部分我们尚未进行充分研究。因此，实现一个内核态客户端模块最终是不可避免的。
